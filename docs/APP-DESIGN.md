## 2. 产品定义

### 2.1 目标场景

**单人自用、多台设备、以看为主**：IT 爱好者/小团队运维，在手机上随时看家里或机房的几台机器（NAS、软路由、PVE、云主机）跑得怎么样，偶尔做一次「批准新设备入网」「加个节点」这种轻操作。

不是给多人协作的 SaaS 面板，因此：

- 不做账号体系，一个面板一个管理员密码；
- 不做服务端多租户，面板 = 一个独立的 Master 实例。

### 2.2 明确不做（Non-goals）

| 不做 | 原因 |
|---|---|
| SSH / PVE / 群晖节点的凭据录入 | 字段多、易错，且失败重试体验差，留在 Web 后台做 |
| 程序池 / OTA 上传（multipart ≤256MB） | 手机端无意义，留在 Web 后台 |
| 修改告警通知渠道（SMTP/机器人 Webhook） | 配置繁琐，属于一次性配置 |
| 历史数据导出 CSV | 手机上下载文件价值低 |
| 后台常驻推送 | 服务端无推送服务，详见 8.5 |
| 多语言（首版仅简体中文） | 后续按需 |

### 2.3 非功能需求

| 项目 | 目标 |
|---|---|
| 冷启动到首页有内容 | ≤ 1.5 秒（含本地缓存首屏） |
| 首页节点数据新鲜度 | WS 实时（一般 5 秒一刷）；断线时 30 秒轮询 |
| 仪表盘动画 | 300ms，数值变化不闪烁 |
| 单面板流量 | 10 节点约 0.6 KB/s（WS），后台为 0 |
| 内存占用 | 列表 100 节点内 < 150 MB |
| 电量 | 前台 WS + 后台断连，亮屏使用 1 小时 < 5% |

## 3. 页面结构与导航

### 3.1 页面地图

```
启动
 ├─ 冷启动 ─→ 读本地面板配置
 │              ├─ 无面板 ─→ 引导页（新增面板）
 │              └─ 有面板 ─→ 首页（先渲染缓存，再拉新）
 │
首页（底部导航）
 ├── 概览  ├── 告警  ├── 设备？（无，点卡片进详情）  └── 设置
 │
 ├─ 点节点卡片 ─→ 设备详情
 │                 ├─ 实时
 │                 ├─ 历史曲线
 │                 ├─ 系统/硬件
 │                 └─ 事件/告警
 │
 ├─ 告警 Tab ─→ 全面板告警聚合列表（按状态/级别/节点筛选，WS 实时刷新）
 │
 └─ 设置 Tab
      ├─ 面板列表 ─→ 面板编辑（显示开关 / 节点可见性 / 登录状态 / 删除）
      ├─ 新增面板 ─→ 输入地址 + 密码 → 测试连接 → 选择显示节点
      ├─ 节点管理 ─→ 节点列表（含待审批）→ 添加节点 / 批准
      └─ 通用（主题、刷新、缓存、关于）
```

底部导航 3 个 Tab：**概览 / 告警 / 设置**。「添加节点」藏在设置里，避免低频操作占用主界面。

### 3.2 关键流程 1：首次登录一个面板

```
┌─ 新增面板页 ────────────────────────────┐
│ 面板地址  [192.168.1.10        ]  :8080 │
│ 管理员密码 [••••••••          ]  👁     │
│              [测试并保存]                │
└──────────────────────────────────────────┘
        ↓ 点「测试并保存」
 ① 地址规范化（补 scheme/端口，见 4.2）
 ② GET  /api/v1/auth/status
      ├ admin_set=false → 红字：「面板尚未初始化，请先用浏览器打开并设置管理员密码」
      └ admin_set=true  → 继续
 ③ POST /api/v1/auth/login  {password, scope:"admin"}
      ├ 401 → 红字：「密码错误」（连续 5 次会被服务端临时锁定 → 429，提示等待秒数）
      └ 200 → 拿到 Set-Cookie: cc_session
 ④ GET  /api/v1/auth/whoami  → 确认 scope=admin
 ⑤ POST /api/v1/auth/api-keys  {name:"<设备名>", scope:"admin"}
      └ 拿到本机专属 cck_...（明文仅此一次）→ 存进加密偏好
 ⑥ GET  /api/v1/nodes        （用 Key 预热首屏；此后会话 Cookie 可丢弃）
 ⑦ 保存面板（地址 + Key + 可选密码）
 ⑧ 进入「选择首页显示节点」（全选默认）
```

一次成功登录后，**不再需要用户输入密码**——本机 Key 长期有效，直到用户在面板里吊销它。

### 3.3 关键流程 2：审批新设备

```
设置 → 节点管理
  → 列表顶部单独分组「待审批 (2)」  ← 来自 GET /nodes 中 approved=false
  → 点某条 → 底部弹层：设备名 / 系统类型 / 地址 / 申请时间
       [拒绝（删除）]   [批准]
  → 批准：PUT /nodes/:id  {"approved": true}
  → 该条移出「待审批」，进入正式列表
```

> ⚠️ 只有 **admin** 身份的会话才能看到并审批 pending 节点（`GET /nodes` 对非管理员直接过滤掉）。因此面板必须用管理员密码登录，这一点在 4.1 有专门讨论。

## 4. 认证与多面板（核心设计）

### 4.1 「地址 + 密码」怎么落地：三种方案

用户需求是「输入面板地址和后台密码就能看到所有设备」。后端现有两种凭证，各有代价：

| | 会话 Cookie | API Key（Bearer） |
|---|---|---|
| 获取方式 | `POST /auth/login` 用密码换 | 先用管理员会话调 `POST /auth/api-keys` 签发（每设备一条） |
| 有效期 | **固定 7 天**，无刷新接口 | 长期有效，直到该条被吊销 |
| 多设备 | 每台设备独立会话，互不影响 | **每条 Key 独立**，吊销 A 不影响 B ✅ |
| 权限 | `admin` / `view` 可选 | `admin` 或 `view`（签发时定死） |
| 服务端状态 | 无（无状态 HMAC） | 一条 `api_keys` 记录（可命名、可审计） |

> **v1.2 已实现多凭证**：`api_keys` 表 + `/auth/api-keys` 接口，每台设备各签一条。
> 早期版本只有一个 Key slot（`settings.api_key_hash`），新生成会把旧 Key 踢下线——该限制已解除，
> 旧接口 `/auth/api-key/rotate` 保留为「操作 `default` 那一条」的兼容路径。

三种方案：

#### 方案 A（推荐）：密码 → 签发专属 API Key

- 用户输入「地址 + 密码」，App 用一次 `POST /auth/login` 换取管理员会话；
- 立刻 `POST /auth/api-keys {name: "我的手机", scope}` 签一条**属于本机的 Key**，把明文存进加密偏好；
- 之后**全程 Bearer**，不存密码、不管 Cookie、不会过期；
- 多设备互不影响，卸载重装重新签一条即可；
- 代价：本机 Key 泄露等价于该面板的对应权限，可在面板里单独吊销。

#### 方案 B（更保守）：密码 → 会话 Cookie

- 只存密码（加密），7 天静默重登；
- 适合不想在服务端留凭证记录的场景；
- 代价：本地必须存密码，7 天一次重登。

#### 方案 C（已落地）：多 Key 列表

- 即方案 A 依赖的后端能力，已实现：`GET/POST/DELETE /auth/api-keys`；
- 面板里能看到「谁在什么时候签了什么权限的 Key」，便于按设备吊销。

**结论**：首版走 **方案 A**（换 Key 后只存 Key，不存密码）。设置里保留一个可选开关：

- 「同时记住密码」关闭（默认）：只存 Key，最干净；
- 开启：额外存密码，用于 Key 被吊销后自动重新签发（适合自用单机）。

### 4.2 地址规范化

用户输入五花八门，必须统一处理，否则首次连接就失败：

| 用户输入 | 规范化结果 |
|---|---|
| `192.168.1.10` | `http://192.168.1.10:8080` |
| `192.168.1.10:8080` | `http://192.168.1.10:8080` |
| `192.168.1.10:8080/` | `http://192.168.1.10:8080` |
| `http://nas.local` | `http://nas.local:8080` |
| `https://dash.example.com` | `https://dash.example.com`（443 不补端口） |
| `dash.example.com/cc` | `http://dash.example.com:8080/cc`（反代子路径，需保留） |

规则：

1. 不含 `://` 时默认补 `http://`；
2. `http://` 且未写端口时补 `:8080`；`https://` 未写端口时补 `:443`（或不补，交给 URL 默认值）；
3. 去掉结尾 `/`；
4. 保留路径前缀（后面拼 `/api/v1`）；
5. 保存规范化后的地址，同时保留用户原始输入用于回显。

**明文 HTTP 必须在 `network_security_config.xml` 里放行**，否则 Android 9+ 直接抛 `Cleartext HTTP traffic not permitted`。由于地址由用户填写、事先无法枚举，只能用 `base-config cleartextTrafficPermitted="true"`（内网工具可接受），详见 `APP-API.md` 7.1。

### 4.3 面板数据模型

多面板是本地概念，后端无感。**核心约束：`node.id` 只在某个面板内唯一，不同面板会出现相同 id**，所以本地所有引用必须用复合键 `(panelId, nodeId)`。

```kotlin
// 面板（存本地数据库）
data class Panel(
    val id: Long,              // 本地自增，非服务端 ID
    val name: String,          // 用户可改，默认取站点标题或主机名
    val baseUrl: String,       // 已规范化，如 http://192.168.1.10:8080
    val rawInput: String,      // 用户原始输入，仅回显
    val siteTitle: String,     // GET /site 的 title
    val credential: Credential,
    val showOnHome: Boolean,   // 需求 5：哪些面板上首页
    val nodeFilter: NodeFilter,// 需求 5：该面板显示哪些节点
    val sortOrder: Int,
    val lastOkAt: Long,        // 上次成功请求时间
    val lastError: String,     // 最近一次失败原因，用于列表红点提示
)

sealed interface Credential {
    // 主路径（推荐）：本机专属 Key；可选同时保存密码，用于 Key 被吊销后自动重签
    data class ApiKey(
        val key: String,        // cck_...，加密存储
        val keyId: Long,        // 服务端记录 id，便于面板里对照吊销
        val scope: String,      // admin | view
        val password: String? = null,
    ) : Credential

    // 备选：不签 Key，只用会话 Cookie + 密码
    data class Password(val password: String) : Credential
}

sealed interface NodeFilter {
    object All : NodeFilter                        // 默认
    data class Only(val nodeIds: Set<Long>) : NodeFilter
}
```

节点可见性存 `Set<Long>` 而非 `Set<(panelId,nodeId)>`，因为 filter 挂在 panel 上，天然带面板维度。

**设计细节**：节点被删除后，`nodeIds` 里会残留无效 id——展示时以服务端返回的列表为准做交集，不主动清理（用户可能只是临时不可见）。

### 4.4 凭据存储

| 数据 | 存储位置 | 加密 |
|---|---|---|
| 面板列表（含地址、显示开关、节点过滤） | Room / DataStore | 否 |
| Cookie（`cc_session`） | 加密偏好 | 是 |
| 密码（可选） | 加密偏好 | 是 |
| API Key（若启用） | 加密偏好 | 是 |

用 Jetpack `EncryptedSharedPreferences` + `MasterKey`（`androidx.security:security-crypto`）。注意：

- **不要**把密码/Key 写进 `BuildConfig`、`strings.xml`、日志；
- 崩溃上报/日志里对 `Authorization`、`Cookie` 头做脱敏；
- 用户可在设置里「清除所有凭据」一键退出全部面板。

### 4.5 会话生命周期

采用方案 A（本机 Key）后，日常几乎没有「会话过期」这回事——Key 不过期：

```
首次添加面板
  └→ POST /auth/login 换会话 → POST /auth/api-keys 签本机 Key → 存 Key → 丢弃会话

App 启动 / 回到前台
  └→ 对每个面板并发 GET /auth/whoami（带 Bearer）
        ├ scope 非空   → Key 有效，继续
        ├ scope 为空   → Key 已被吊销 / 面板数据被重置
        │     ├ 存了密码 → 重新 login + 重签 Key，静默恢复
        │     └ 无密码   → 标记「需要重新登录」，点进面板时弹登录框
        └ 网络错误     → 标记「离线」，保留缓存数据展示
```

若用方案 B（Cookie 会话），则退化为：会话固定 7 天、无刷新接口，到期用保存的密码静默重登。
两种模式下失败原因通常只有两个——面板改密码了、面板重装/换库了——都要用户重新输入，**不要自动重试刷请求**。

### 4.6 多面板隔离原则

```kotlin
// 每一层都必须带 panelId，禁止出现「全局当前面板」隐式状态
class NodeRepository(private val panelId: Long) { ... }
```

- **数据层**：每个面板一个 `PanelSession` 实例（持有独立的 OkHttp `CookieJar` 与 `WebSocket`）；
- **缓存**：缓存键统一 `(panelId, nodeId)`；
- **UI 层**：首页分组渲染，每组一个 section header；只有一个面板时隐藏 header；
- **告警页**：跨面板聚合，每条告警带面板名角标，点击进对应面板的详情；
- **错误**：某个面板登录失效不影响其它面板渲染（部分成功也是成功）。

## 5. 首页设计

### 5.1 整体结构（多面板分组）

```
┌────────────────────────────────────────┐
│ CC_DashBoard           [🔍]  [⟳]      │  ← 顶栏：标题(可配) / 搜索 / 刷新
├────────────────────────────────────────┤
│ ● 12 在线   2 离线   1 告警            │  ← 汇总条（跨所有显示中的面板）
├────────────────────────────────────────┤
│ 家里 NAS                    3 台  [⋯] │  ← 面板分组头（仅多面板时显示）
│ ┌──────────────┐ ┌──────────────┐     │
│ │ 节点卡片      │ │ 节点卡片      │     │
│ └──────────────┘ └──────────────┘     │
├────────────────────────────────────────┤
│ 机房 PVE                    5 台  [⋯] │
│ ┌──────────────┐ ┌──────────────┐     │
│ │ 节点卡片      │ │ 节点卡片      │     │
│ └──────────────┘ └──────────────┘     │
└────────────────────────────────────────┘
│  [概览]      [告警]       [设置]       │
└────────────────────────────────────────┘
```

**布局决策**：

| 场景 | 表现 |
|---|---|
| 1 个面板 | 不显示分组头，直接平铺卡片 |
| 多个面板 | 分组渲染；分组头显示面板名 + 节点数 + 在线数；分组头固定（sticky）可选 |
| 手机竖屏 | 1 列（卡片为宽卡片） |
| 平板 / 横屏 | 2 列；`≥840dp` 可 3 列 |
| 某面板加载失败 | 该分组显示错误条 + 「重试」，其它分组正常 |

**排序**：面板按 `sortOrder`；组内节点按服务端 `sort_order`（`GET /nodes` 已排好），App 不再重排，但提供「离线排最后」的本地开关（默认关，保持与 Web 一致）。

### 5.2 节点卡片信息架构

对齐 Web 端首页卡片（`web/src/views/Overview.vue`）的实际内容，并把进度条升级为仪表盘：

```
┌──────────────────────────────────────────┐
│ ●  nas01            [linux]  [↑可升级]   │  ← 状态灯 + 名称 + 系统徽标 + 升级标记
│    192.168.1.10 · 203.0.113.7            │  ← 内网 + 公网 IP（无公网则只显示内网）
│                                          │
│    ◔ 42%      ◔ 63%      ◔ 55%          │  ← 三个仪表盘：CPU / 内存 / 磁盘
│    CPU       内存        磁盘             │
│                                          │
│ ─────────────────────────────────────    │
│ ↑ 320 KB/s   ↓ 1.2 MB/s    运行 12天5小时 │  ← 上下行速率 + 运行时长
└──────────────────────────────────────────┘
```

字段来源（全部来自 `GET /nodes` 的单个节点对象）：

| 界面元素 | 字段 | 说明 |
|---|---|---|
| 状态灯 | `status` | `online` 绿 / `alert` 红（脉冲）/ `offline` 灰 |
| 名称 | `name` | — |
| 系统徽标 | `os_type` | `linux`/`windows`/`nas`/`openwrt`/`darwin`/`pve`/`esxi` → 对应图标或字母 |
| 可升级 | `upgrade` | 字段存在才显示（仅 admin 且池中有新版时） |
| 内网地址 | `address` | 空则不显示 |
| 公网 IP | `public_ip` | 空则不显示 |
| CPU % | `latest.cpu` | 保留整数 |
| 内存 % | `latest.mem_used / latest.mem_total * 100` | **API 没有 mem_pct，必须自算**；`mem_total=0` 时显示 `—` |
| 磁盘 % | `latest.disk_pct` | — |
| 上传速率 | `latest.net_tx` | **`↑` 对应 `net_tx`**（Web 端 title="上传"） |
| 下载速率 | `latest.net_rx` | **`↓` 对应 `net_rx`** |
| 运行时长 | `latest.uptime` | 秒 → 「12天5小时」 |

**离线卡片**：`status=offline` 时三个仪表盘置灰、数值显示 `—`（**不要显示 0%**，会把"没数据"误报成"很空闲"），底部显示「离线 · 最后在线 3 小时前」（用 `last_seen` 算）。

**`latest` 缺失**（新加节点还没上报过）：整块指标区显示「等待首报数据」，仪表盘留空环。

### 5.3 仪表盘规格

Web 端用的是横向进度条，App 要求仪表盘（圆环/半圆）。规格如下：

**形状**：270° 圆环（起点 135°，顺时针），缺口在正下方；圆心显示数值 + 单位。

```
        ╭───────╮
      ╱           ╲
     │     ◜◝      │      ← 轨道：圆角端点，宽 8dp，颜色 #1e293b
     │   42 %      │      ← 进度：圆角端点，宽 8dp，颜色随阈值
      ╲           ╱
        ╰─     ─╯         ← 缺口朝下
```

**阈值配色**（与 Web 端 `Overview.vue` / `DeviceDetail.vue` 完全一致）：

| 值 | 颜色 | 语义 |
|---|---|---|
| `< 75%` | 绿 `#10b981`（emerald-500） | 正常 |
| `75% ~ 89%` | 黄 `#f59e0b`（warning） | 注意 |
| `≥ 90%` | 红 `#ef4444`（danger） | 告警 |

**尺寸**：卡片内单环直径约 64dp；详情页主环 120dp；文字 `42%` 用 14sp/600，标签 `CPU` 用 11sp 灰色。

**动画**：数值变化用 300ms `animateFloatAsState` + `easeOutCubic`；**首次进入不动画**（避免整屏扫动），只在增量更新时动画。

**实现要点**（不引第三方库，Compose `Canvas` 自绘）：

1. `drawArc` 画轨道（背景）与进度（前景），`useCenter=false`，`style=Stroke(width, cap=Round)`；
2. 起始角 `135f`，扫过角 `270f * percent/100f`；
3. 剩余 90° 缺口不加任何装饰；
4. 中心文本用 `drawText` 或 `Box` + `Text` 叠放（后者更省事，但要注意基线对齐）。

**数据边界**：`percent` 做 `coerceIn(0f, 100f)`；`NaN`/`null` 一律按「无数据」渲染空环，不画进度。

### 5.4 网络速率区

- 展示 **`net_rx`（下载 ↓）** 与 **`net_tx`（上传 ↑）**，单位 Bytes/s，格式化规则与 Web 一致：
  - `< 1024` → `B/s`（无小数）
  - 依次 `/1024` 进位 `KB/s` / `MB/s` / `GB/s`
  - 值 ≥ 100 时取整，否则保留 1 位小数
- 图标方向：**↑ = 上传 = `net_tx`**，**↓ = 下载 = `net_rx`**（这对容易写反，写反了用户会看不出异常，务必按此实现）。
- 首页卡片只显示**合计**；分网卡明细在详情页（`live.nics[]`）。
- 离线时显示 `—`，不显示 `0 B/s`。

### 5.5 状态与告警标识

| 服务端 `status` | 展示 | 备注 |
|---|---|---|
| `online` | 绿点 + 「在线」 | — |
| `alert` | 红点 + 呼吸动画 + 「告警」 | 服务端已把「在线且有 firing 告警」改写为 `alert` |
| `offline` | 灰点 + 「离线」 | 同时显示最后在线时间 |

一个节点同时有多个告警时，卡片不展开告警详情（避免卡片高度跳动），只显示红点；点进详情看「当前告警」。

### 5.6 节点筛选与排序

三个层级的筛选，优先级从高到低：

1. **面板级**（需求 5，持久化）：`NodeFilter.Only(setOf(id))` —— 该面板只显示选中的节点；
2. **全局状态筛选**（首页顶栏，会话级）：全部 / 在线 / 告警 / 离线；
3. **搜索**（首页顶栏，会话级）：按 `name` / `address` / `public_ip` 模糊匹配，忽略大小写。

**筛选后为空**时不要显示「没有设备」，要区分：

| 情况 | 文案 |
|---|---|
| 该面板 `nodeFilter` 选中的节点全被删除 | 「该面板暂无可见节点，去设置里调整」+ 跳转 |
| 搜索/状态筛选无结果 | 「没有匹配的设备」+ 「清除筛选」 |
| 面板本身 0 节点（服务端真没节点） | 「这个面板还没有添加节点」+ 「去添加」 |

### 5.7 加载与缓存

**三级状态**：本地缓存 → 网络刷新 → 实时推送。

```
冷启动
 ├ 读本地缓存（上次的节点列表 + 时间戳）→ 立刻渲染（灰一点，标记「缓存」）
 ├ 并发 GET /nodes（所有显示中的面板）
 │    ├ 成功 → 覆盖缓存、去掉「缓存」标记
 │    └ 失败 → 顶部提示条「部分面板连接失败」+ 重试
 └ 连 WS → 增量更新
```

- **下拉刷新**：`RefreshIndicator`，只刷当前可见分组对应的面板。
- **自动刷新**：WS 正常时不轮询；WS 断开时降级为 30 秒 `GET /nodes`。
- **缓存保留期**：7 天；超期清空，避免看到陈旧数据误判。
- **缓存内容**：节点列表 + 每个节点的 `latest`，**不缓存历史曲线**（体积大、时效性弱）。

## 6. 设备详情页

### 6.1 数据来源与时序

```
进入详情
 ├ GET /nodes/:id/detail        ← 首屏全量（node/latest/live/detail/hardware/events/boot_events/alerts）
 ├ GET /nodes/:id/history?range=24h   ← 默认 24 小时曲线
 └ 订阅 WS 中 node_id 匹配的 metrics / live 消息 → 就地刷新实时区
```

- 首屏用 `detail` 接口一次拿全，**不要**拆成多个请求（多请求在弱网下体验差）。
- WS 消息到达时只更新「当前实时」区与卡片顶部状态，**不重绘历史曲线**。
- 切走再回来：`live` 数据可能已过期 >1 分钟，需重新拉一次 `detail`。

### 6.2 页面分区（对齐 Web 端详情页）

Web 端详情页有 22 个区块标题，App 按「信息价值 + 屏幕尺寸」重组为 6 段折叠区：

| # | App 区块 | 内容 | 数据来源 |
|---|---|---|---|
| 1 | **顶部概览** | 名称、状态、系统、IP、运行时长、首次采集时间 | `node` |
| 2 | **实时指标** | 三个大仪表盘（CPU/内存/磁盘）+ 上/下行 + 负载 | `latest` + WS `metrics` |
| 3 | **历史曲线** | range 选择器 + 4 张图（CPU/内存/网络/磁盘 IO） | `history` |
| 4 | **实时明细** | 每核 CPU、内存细分、温度、分网卡速率、进程 Top5 | `live`（WS 推送） |
| 5 | **系统与硬件** | 主机名/内核/架构、挂载点、CPU 型号、内存条、主板、磁盘、网卡 | `detail` + `hardware` |
| 6 | **事件与告警** | 当前 firing 告警、近期上下线、开关机记录 | `alerts` + `events` + `boot_events` |

排列顺序即用户关心的顺序：**实时 → 趋势 → 细节 → 静态信息 → 历史事件**。第 5、6 段默认折叠（用 `ExpandableSection`），减少滚动长度。

### 6.3 实时明细（`live`）

`live` 是**自由结构**（由采集端决定），App 必须容错解析：

| 子结构 | 字段 | 用途 |
|---|---|---|
| 顶层 | `cpu_total`、`per_cpu[]`、`load1/5/15` | 每核柱状图 + 负载 |
| `mem` | `total/used/available/free/buffers/cached/swap_*/percent` | 内存堆叠条（已用/缓存/空闲） |
| `disk_io` | `read_bps/write_bps/read_count/write_count` | 磁盘 IO 实时 |
| `nics[]` | `name/rx_bps/tx_bps/mac/ipv4` | 分网卡速率表 |
| `temps[]` | `label/value` | 温度标签 |
| `procs[]` | `pid/name/cpu/mem` | 进程 Top5 表 |
| `vms[]`（PVE） | `vmid/name/status/type` | 虚机/容器列表（仅 PVE 节点） |

**解析策略**：用 `JsonObject` + 可选取值，任何一段缺失就**隐藏该段**，不要显示空表或 `NaN`。字段名大小写、驼峰/下划线都按文档写死（服务端透传，无统一约定）。

### 6.4 历史曲线

| range | 标签 | 返回点数 | 说明 |
|---|---|---|---|
| `1h` | 1 小时 | ≤ 720（5 秒粒度） | 实时性最好 |
| `24h` | 24 小时 | ≤ 1440（1 分钟） | **默认** |
| `7d` | 7 天 | ≤ 10080 | **必须先降采样再画** |
| `30d` / `180d` / `365d` | 30 天 / 半年 / 一年 | ≤ 720 / 4320 / 8760 | 1 小时粒度 |

**实现要点**：

1. `points[].per_cpu` 是**字符串** `"[12.5,8.3]"`，要 `Json.decodeFromString<List<Double>>` 二次解析；空串 = 该窗口无数据。
2. 降采样：目标是屏幕宽度对应的点数上限（如 2 倍宽度，约 800 点）。用 LTTB（Largest-Triangle-Three-Buckets）或简单的 min/max 分桶，保留峰值形态。
3. `mem_pct` 不存在，画内存曲线时用 `mem_used/mem_total*100` 逐点算。
4. 图表选型：Vico（Compose 原生）或自绘 Canvas；MPAndroidChart 是 View 体系，需要 `AndroidView` 包装。
5. range 切换时**保留旧图**直到新数据到达（避免闪白），加 loading 遮罩。

### 6.5 空数据形态（必须按此处理）

实测空态（新节点、无历史、无告警）：

```json
{"latest":null,"live":null,"detail":null,"hardware":null,"events":null,"boot_events":[],"alerts":[]}
```

| 字段 | 空值形态 | UI 表现 |
|---|---|---|
| `latest` | `null` | 仪表盘画空环 + 「等待首报数据」 |
| `live` | `null` | 隐藏「实时明细」整段 |
| `detail` / `hardware` | `null` | 隐藏「系统与硬件」段 |
| `events` | **`null`** | 显示「暂无事件」 |
| `boot_events` | `[]` | 显示「暂无开关机记录」 |
| `alerts` | `[]` | 显示「当前无告警」 |

注意 `events` 是 `null` 而 `boot_events` 是 `[]`——**不要写统一的空判断**。

## 8. 实时数据与刷新策略

### 8.1 WS 连接管理

- **每个「首页显示」的面板各一条 WS**，最多 3 条（超过 3 个则只连前 3 个，其余面板靠轮询）；
- 连接 URL：`ws(s)://<host>/api/v1/ws`，鉴权用**同一份 Cookie**（App 内 OkHttp 会自动带 Cookie）；
- 只有 App 处于**前台**且当前 Tab 是「概览/详情」时保持连接；进入后台 30 秒后全部断开；
- 详情页在概览 WS 基础上不再新建连接，复用并按 `node_id` 过滤。

### 8.2 消息分发

```
WS 消息
 ├ type=metrics     → 按 node_id 更新对应卡片 + 详情页实时区
 ├ type=live        → 仅当详情页正在看该节点时消费（否则丢弃，省内存）
 ├ type=node_status → 更新状态灯；触发一次 GET /summary 校准计数
 ├ type=node_added  → 该面板标记「列表待刷新」，回到首页时拉 GET /nodes
 ├ type=node_removed→ 立即从列表移除，若正在看该节点详情则退回首页
 ├ type=node_pending→ 设置 Tab 打红点，刷新待审批分组
 ├ type=alert_firing  → 插入/更新告警列表，Tab 打红点（比轮询及时）
 └ type=alert_resolved→ 从 firing 列表移除
```

**不要**收到 `metrics` 就整表重载——只更新对应 item，用 `DiffUtil`/`key` 保证其它卡片不重组。

### 8.3 重连与退避

```
断线（onFailure / onClosed）
 └ 指数退避：1s → 2s → 4s → 8s → 15s → 30s（上限 30s，每次成功连接后重置）
 └ 退避期间改用 30 秒 GET /nodes 轮询兜底
 └ 重连成功 → 立即 GET /nodes 重新对齐（断线期间消息不会补发）
```

**保活**：OkHttp `pingInterval(20s)`，客户端发 PING、服务端 gorilla 自动回 PONG，能及时发现半开连接。

### 8.4 前后台切换

| 事件 | 动作 |
|---|---|
| 进后台 | 30 秒后断开 WS、停止轮询（省电） |
| 回前台 | 立即 `GET /nodes` + 重连 WS + 检查会话（`/auth/whoami`） |
| 屏幕熄灭 | 等同后台 |

### 8.5 关于后台通知（重要限制）

服务端**没有**推送通道（无 FCM、无 Webhook 到 App）。因此：

- 首版**不做**实时告警推送；
- 可选实现：`WorkManager` 每 15 分钟（系统最小周期）拉一次 `/alerts?status=firing`，有新告警就发本地通知。缺点：延迟最大 15 分钟，且部分厂商 ROM 会限制后台任务。
- 真要秒级推送，需要服务端接推送服务（见第 14 章），属于另一个工程。

## 9. 技术架构建议

### 9.1 分层

```
UI (Compose)
  ├ HomeScreen / DetailScreen / AlertsScreen / SettingsScreen
  ↓
ViewModel（每个面板一个 VM 实例，或共享 VM + panelId 参数）
  ↓
Repository（PanelSession 持有 CookieJar / WS / 缓存）
  ↓
DataSource
  ├ Remote：OkHttp + kotlinx.serialization（REST）、OkHttp WebSocket
  └ Local ：Room（面板、节点缓存）+ DataStore/EncryptedSharedPreferences（凭据、设置）
```

### 9.2 多面板状态隔离

```
HomeViewModel
  └ state: Map<panelId, PanelUiState>
        data class PanelUiState(
            val panel: Panel,
            val status: ConnStatus,        // 连接中 / 已连接 / 离线 / 需登录
            val nodes: List<NodeUi>,       // 已按 nodeFilter 过滤
            val summary: Summary?,         // total/online/alerting
            val cacheAgeSec: Long,
        )
```

- 单面板失败只影响 `PanelUiState.status`，不影响其它条目；
- 首页汇总条由各面板 `summary` 相加得出（服务端 `/summary` 是单面板维度）。

### 9.3 本地存储表

```sql
-- 面板
CREATE TABLE panel (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  base_url TEXT NOT NULL,
  raw_input TEXT,
  site_title TEXT,
  show_on_home INTEGER NOT NULL DEFAULT 1,
  node_filter TEXT,            -- NULL=全部；JSON 数组=Only
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,
  last_ok_at INTEGER
);

-- 节点缓存（复合主键，防跨面板冲突）
CREATE TABLE node_cache (
  panel_id INTEGER NOT NULL,
  node_id INTEGER NOT NULL,
  name TEXT,
  os_type TEXT,
  status TEXT,
  payload TEXT NOT NULL,       -- 完整节点 JSON，含 latest
  fetched_at INTEGER NOT NULL,
  PRIMARY KEY (panel_id, node_id)
);

-- 告警缓存（可选，用于离线看告警）
CREATE TABLE alert_cache (
  panel_id INTEGER NOT NULL,
  alert_id INTEGER NOT NULL,
  status TEXT,
  payload TEXT NOT NULL,
  fetched_at INTEGER NOT NULL,
  PRIMARY KEY (panel_id, alert_id)
);
```

缓存 `payload` 直接存原始 JSON 字符串最省事——服务端字段变化时不会因为本地表结构过时而解析失败。

### 9.4 列表性能

- `LazyColumn` + `key = { it.panelId to it.nodeId }`（复合键，避免跨面板 id 冲突导致重组错乱）；
- 卡片内仪表盘用 `Canvas` 自绘，不开动画的静态态要能复用（`remember`）；
- 100 条以内无需分页；超过 100 条时按面板分组懒加载（组内 `LazyColumn` 嵌套需要固定高度，建议改用单层 LazyColumn + sticky header）。

### 9.5 依赖建议（保持精简）

| 用途 | 建议 |
|---|---|
| 网络 | OkHttp（REST + WS 共用同一 client） |
| JSON | kotlinx.serialization（配 `ignoreUnknownKeys=true`） |
| 图片/图标 | 仅需矢量图标，用 Material Icons，不引图片库 |
| 数据库 | Room |
| 偏好 | DataStore + `security-crypto` |
| 图表 | Vico 或自绘（不建议 MPAndroidChart，View 体系在 Compose 里要额外包装） |
| DI | 手动构造或 Hilt（面板数量少，手动也够） |

## 10. 错误处理矩阵

| 场景 | 检测方式 | UI 表现 | 恢复动作 |
|---|---|---|---|
| 面板地址不可达 | `ConnectException` / `UnknownHostException` | 分组内红条「无法连接」 | 重试按钮；检查地址/网络 |
| 明文 HTTP 被系统拦 | `CleartextNotPermittedException` | 引导弹窗 | 提示检查 network_security_config（开发期问题） |
| 密码错误 | `POST /auth/login` → 401 | 输入框下方红字 | 重输 |
| 面板未初始化 | `GET /auth/status` → `admin_set=false` | 提示去浏览器初始化 | 无（需人工） |
| 会话过期且无密码 | `/auth/whoami` → `scope=""` | 分组显示「需要登录」 | 点击弹登录框 |
| 会话过期且有密码 | 同上 | 静默重登（无 UI） | 失败则转上一条 |
| 用 `view` 权限做写操作 | 写接口 → 401 且 message=「需要管理员登录」 | 「当前面板无管理员权限」 | 不影响本地凭据（**不要**因此清密码） |
| 节点已被删除 | `/nodes/:id/detail` → 404 | 「设备已删除」+ 返回 | 返回首页并刷新 |
| 服务端 500 | 状态码 500 | 通用错误条 + 重试 | 重试 |
| WS 反复失败 | 连续 N 次 `onFailure` | 顶部「实时更新已断开，正在重试」 | 自动退避；可选择关闭 WS |

**401 的统一处理**是关键：401 有三种含义，必须靠 `message` 区分——「需要访问密码 / 需要管理员登录」是权限问题（**不要清本地密码**），只有 `/auth/login` 返回 401 才是密码错。

## 11. 安全与隐私

| 项 | 措施 |
|---|---|
| 密码/Key 存储 | `EncryptedSharedPreferences`（AES-GCM，密钥存 Keystore） |
| 日志 | 禁止打印 `Authorization` / `Cookie` / `password`；OkHttp `HttpLoggingInterceptor` 在 release 构建必须关闭（或 `redactHeader`） |
| 截屏 | 可选：`FLAG_SECURE`（默认关闭，用户自己选） |
| 明文传输 | 内网自用可接受；公网必须上 HTTPS（反代），App 侧不建议做「忽略证书错误」 |
| 自签证书 | 若面板用自签 HTTPS，提供「信任此面板证书」（`network_security_config` 里按域名加 `<trust-anchors>`），**不要全局关闭证书校验** |
| 凭据泄露 | 面板地址 + 密码足以拿到完整控制权，设置里提供「一键清除所有凭据」 |
| 备份 | `android:allowBackup="false"`（避免密码随云备份外泄） |

## 12. 兼容性与边界情况

| 场景 | 处理 |
|---|---|
| **多个面板有相同 node.id** | 全部用 `(panelId, nodeId)`，禁止裸用 `nodeId` |
| 面板改了密码 | 静默重登失败 → 标红提示重输，其它面板不受影响 |
| 面板被重装（数据库清空） | 会话失效 + 节点全部 404 → 提示「面板数据已重置」 |
| 用户手机时区/时间不准 | 所有时间戳以服务端 Unix 秒为准，只在展示时转本地时区 |
| 节点 `latest` 缺失 | 显示「等待首报数据」，不显示 0% |
| `mem_total = 0` | 内存百分比显示 `—`（避免除零得 `NaN`/`Infinity`） |
| 节点数 > 200 | 列表加搜索优先；WS 消息量增大，考虑只对可见分组保持 WS |
| 服务端升级、API 加字段 | `ignoreUnknownKeys=true` 保证不崩；关键接口封装处集中处理 |
| 横竖屏切换 | 详情页曲线图需保存 range 选择，不重置 |
| 弱网（<100KB/s） | 首屏只拉 `/nodes`（不带 detail），进详情再拉 detail |
